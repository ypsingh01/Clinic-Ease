SDLC PHASE 1: REQUIREMENT ANALYSIS
1.1 Purpose
ClinicEase digitizes appointment scheduling for a clinic with 5-6 doctors, replacing
manual/phone-based booking with a self-serve online system that reduces admin
workload, prevents double-booking, and keeps patients informed automatically.
1.2 Stakeholders
Stakeholder Interest
Patient Book/manage appointments easily, get reminders
Doctor Control availability, see daily patient load
Admin/Reception Oversee all bookings, handle walk-ins/edge cases, view revenue
Clinic Owner (client) Reduced no-shows, less phone workload, professional online presence

SDLC PHASE 3: FEATURE-BY-FEATURE BREAKDOWN
Each feature below includes: what it does, why it matters, and the key implementation logic
— the level of detail a senior dev would document before coding.
Feature 1: Hourly Capacity Blocks & Token Queue Generation
What: Instead of one exclusive slot per hour, each doctor's hour block (e.g., 10-11 AM) holds
multiple patients based on capacity — derived from an average consultation time (e.g., 5
min - 12 patients/hour). Each booking gets a token number and an initial estimated time =
block start + (token position — 1) x average duration. Why it matters: A real doctor sees far
more patients per hour than a 1-slot-per-hour model allows. Without this, the system either
wastes 90% of actual capacity or forces patients into a misleading shared "10-11" window.
This is the foundation the rest of the booking system builds on. Implementation logic:
« Store availability + capacity as rules (recurring pattern + hourly capacity), not pre-
generated rows for infinite dates

« Generate actual hour-block instances on-demand for a requested date range, showing
"X of 12 spots remaining" rather than a single available/unavailable state

allowing a new token to be issued

+ New token's =block_start + (current queue length) x doctor's

Feature 2: Real-Time Token Booking (No Double-Booking, No Overbooking)

‘What: When a patient books into an hour block, a token is temporarily "held" during
payment; on success it becomes a permanent, sequentially-numbered queue entry; on
failure/timeout it releases and the position becomes available again. Why it matters: This is
the trickiest concurrency problem in the app — multiple patients could request the last
token in a block within milliseconds, and token numbers must stay gap-free and sequential
for the ETA math to hold. Implementation logic:

« UseaDB transaction with on the hour block when assigning
the next so two concurrent bookings can never receive the same
token

« Setashort expiry (e.g., 5 minutes) on held tokens; a background job releases expired
holds and closes the gap in queue positions

+ Emita Socket.io event (queue: updated) so other patients viewing that doctor's block
see remaining capacity and their potential position update live

Feature 2a: Dynamic ETA Recalculation Engine

What: After each consultation is marked complete, the system compares actual duration to
the assumed average and recalculates estimated times for every patient still waiting in the
queue — for that doctor, that day. Why it matters: This is what makes the token system
trustworthy rather than just a nicer-looking version of the same over-promising problem.
Consultations naturally run long or short, and patients need estimates that reflect reality,
not a static assumption made at booking time. Implementation logic:

« Update arolling average (e.g., weighted average of last N consultations that day) into
for that doctor/day

« Recompute for all remaining (booked)/(held) appointments in that
day's queue using the new average and current position

«On cancellation or no-show, shift all subsequent queue positions up by one and
recompute their ETAs

« Onamanual "delay offset" from the doctor (e.g., "+15 min, emergency"), apply a flat
offset to all remaining ETAs in one operation via

« Push updated ETAs via Socket.io (in-app) and a WhatsApp template message to

affected patients — always phrased as an estimate/window, never a guarantee
Feature 3: Booking Flow & Payment Integration
‘What: Patient picks doctor - date - hour block -> confirms -> pays via Razorpay - gets a
token number and estimated time. Why it matters: Payment failure/edge cases (user closes
tab mid-payment, payment succeeds but webhook is delayed) must not corrupt
appointment state. Implementation logic:

« Create Razorpay order server-side first, then open checkout client-side (never trust
client-only payment confirmation)

« Confirm booking only after Razorpay webhook verifies payment signature server-
side — not just the client-side success callback

« Handle webhook idempotency (Razorpay may retry webhooks) using the payment ID
as a unique constraint

Feature 4: Notifications (In-App + WhatsApp)

What: Booking confirmations, reminders (24h/1h before estimated time), cancellations,
reschedules, and live ETA-shift updates (queue moved up/delayed) all trigger both an in-
app notification and a WhatsApp message. Why it matters: This directly delivers the "60%
reduction in manual scheduling effort" value proposition — it's the automation payoff.
Implementation logic:

+ In-app:insertarow into (notifications)table; frontend polls or listens via Socket.io for
new ones

+ WhatsApp: use Twilio's WhatsApp Business API with pre-approved message
templates (required for anything outside a 24h user-initiated session window)

+ Reminder scheduling: a job runs every 15 minutes, queries appointments
starting in ~24h or ~1h windows that haven't been reminded yet, and fires
notifications

Feature 5: Patient Dashboard
What: Upcoming appointments, past history, reschedule/cancel actions, notification center.
Implementation logic:

« Reschedule = cancel old token (release it, shift queue behind it) + create new held
token in a different block, in one transaction

« Cancellation policy enforcement (e.g., no cancellation within 2 hours of appointment)
handled server-side, not just Ul-disabled buttons

» Patient view shows both the estimated time and a live "currently serving token #N"
indicator so a shifting ETA reads as normal system behavior, not an error

Feature 6: Doctor Dashboard

Feature 7: Admin Dashboard

Implementation logic:

Feature 11: Symptom-to-Specialty Helper

What: A simple guided flow — patient selects or types symptoms (e.g., "toothache," "skin
rash," "back pain") — that suggests a specialty and matching doctor(s), for patients unsure
which doctor to book. Why it matters: Reduces booking abandonment for patients who
don't know clinic-specific specialty terms; mirrors a pattern proven at scale by platforms
like Practo. Implementation logic:

» Given a fixed roster of 5-6 doctors, this does not need machine learning — a small
curated lookup table (symptom keyword -> specialty) is
sufficient and far easier to maintain/audit

« Patient input matched against keyword tags (chip-style multi-select is more reliable
than free text for a small clinic; free text can be layered on top with simple keyword
matching later)

« Result shows suggested specialty + doctors in that specialty with current availability
— patient still makes the final choice

« Important safeguard: always display this as general guidance ("Based on what you've
described, you may want to see...") with a visible disclaimer that it is not a medical
diagnosis and urgent symptoms should be treated as such (e.g., a note to call the clinic
directly or seek emergency care for severe symptoms)

Feature 13: Rate Limiting & Bot Protection
What: Protects public-facing endpoints (registration, booking, symptom checker) from
automated abuse — fake token spam, scripted registration floods, or scraping. Why it
matters: A booking system with real payment and limited daily capacity is a natural target
for abuse (e.g., a script grabbing every token in a popular doctor's queue). This needs to be
designed in from the start, not bolted on after an incident. Implementation logic:
+ API-level rate limiting middleware (e.g.,(express-rate-1init)) on (/api/auth/*),
(create), and (7api/symptom-check), keyed by IP and/or account
« CAPTCHA (e.g., Google reCAPTCHA v3, invisible/low-friction) on registration and
the booking confirmation step
« Phone OTP verification (already required for WhatsApp linkage) doubles as a natural
bot deterrent, since it requires a real, reachable phone number
« Logand alert on unusual patterns (e.g., many bookings from one IP in a short window)
for Admin visibility
